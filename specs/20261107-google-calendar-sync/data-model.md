# Data Model: Google Calendar Booking Sync

## IntegrationSettings

Reuse the existing row keyed by `IntegrationProvider`.

- Add `GOOGLE_CALENDAR` to the provider enum.
- `config.calendarId`: validated non-secret destination calendar identifier.
- Existing encrypted AES-256-GCM secret columns store the service-account JSON. The credential is write-only in the UI and never returned by status queries.
- `verifiedAt` is set only after a successful access test that confirms writer access.

## GoogleCalendarBookingEvent

One record per booking once confirmation synchronization is requested.

| Field | Meaning | Invariant |
|---|---|---|
| `id` | Local primary key | Generated by Prisma |
| `bookingRequestId` | Owning reservation | Unique; cascade with reservation |
| `calendarId` | Destination used for this event | Snapshot; deletion does not follow later settings changes |
| `eventId` | Google event resource ID | Stable per booking, valid Google ID alphabet, unique with calendar ID |
| `status` | `PENDING`, `CREATED`, or `DELETED` | Provider success is recorded only after verification |
| `lastFailureCode` | Safe stable failure category | Never contains provider response, credential, or event PII |
| `syncedAt` | Last successful create/delete operation | Nullable until provider success |
| `createdAt`, `updatedAt` | Local timestamps | Managed by Prisma |

The event summary and description are derived from the current reservation at create time, rather than duplicated in the local record. Confirmation jobs only run while the reservation remains awaiting payment. No confirmed-reservation editing is in scope.

## IntegrationJob

Reuse the existing durable outbox and statuses.

- `kind`: a dedicated Google Calendar booking-confirmation handler.
- `idempotencyKey`: unique per booking confirmation; retries reuse the same row.
- `payload`: booking request ID only; do not include credentials or personal data beyond the local ID.
- `lastError`: store only a stable application-owned failure code for this integration.
- Exhausted jobs remain `DEAD` and are explicitly requeued by an authorized operator after access is restored.

## BookingRequest and Payment

- Payment records are committed independently of `CONFIRMED` state when a Google event is pending or unavailable.
- The booking remains `AWAITING_PAYMENT` until event creation is reconciled and a transaction rechecks the booking and payment before the state transition.
- Existing payments are never deleted or rolled back because of Google failures.
- Expiry must not expire an awaiting-payment booking that already has a valid payment and a pending calendar confirmation.

## Cancellation Lifecycle

- If a Google event row is `CREATED`, delete the provider event before the state transition.
- After verified deletion, mark the row `DELETED` and transition to `CANCELLED`.
- On provider failure, leave the event row and booking unchanged so the operator can retry.
- Existing confirmed bookings with no Google event row are not backfilled; cancellation uses the existing local workflow.

## Relationships

```text
BookingRequest 1 ── 0..1 GoogleCalendarBookingEvent
BookingRequest 1 ── 0..N Payment
IntegrationJob   (idempotent confirmation work keyed to BookingRequest)
IntegrationSettings[GOOGLE_CALENDAR] (single configured destination)
```
